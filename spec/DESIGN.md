# BriefAgent — DESIGN

**Architecture (one paragraph).** A single Next.js (TypeScript, Tailwind) app. Run state lives in a **server-side in-memory run store** keyed by `runId` (no database; a run exists only for its own lifetime, which keeps the SPEC's "no storage beyond the run itself"). Four API routes do the work: `/api/plan` (question → sub-questions; creates the run and returns its `runId`), `/api/plan/approve` (records the user's approval of the — possibly edited — plan on the run), `/api/research` (requires a run with an approved plan; runs Exa search + contents per sub-question and stores the retrieved sources on the run), `/api/draft` (requires a run whose research completed; drafts **only from the sources stored on that run** — client-supplied sources are ignored). The gates and source provenance are therefore enforced server-side, not by the UI's good behaviour. The LLM is FastRouter; search/reading is Exa. The client keeps finished briefs in localStorage and exports Markdown. The eval runner drives the same HTTP flow headlessly (plan → approve → research → draft), performing the approvals itself.

**Data model (in-run only; stored server-side in memory, keyed by runId)**
- `Run`: id (runId), question, status (planning → awaiting-plan-approval → researching → drafting → awaiting-draft-approval → final / failed), createdAt, planApproved flag, approved plan, retrieved sources, research warning if any sub-question's search failed.
- `Plan`: subQuestions: string[] (user-editable before approval; the approved, edited version is what gets researched).
- `Source`: id (S1, S2…), url, title, excerpt, subQuestionIndex.
- `Brief`: markdown body with inline `[S#]` citations, conflicts: { claim, positions: [{sourceId, stance}] }[], unverifiedFlags: string[].

**API contracts**
- `POST /api/plan` { question } → { runId, subQuestions } — creates the run. The planner guarantees 3–6 sub-questions: it retries/repairs until at least 3 are produced, or fails with a plain error.
- `POST /api/plan/approve` { runId, subQuestions } → { ok } — records approval of the edited plan on the run. Unknown runId → 404.
- `POST /api/research` { runId } → { sources, warning? } — 409 unless the run's plan is approved. Searches the run's approved sub-questions (identical sub-questions deduped first), one Exa call per sub-question with **per-sub-question settlement**: a failed call does not fail the run — the run proceeds with the sources that succeeded and returns a `warning`; it fails only when zero sources were retrieved. Sources are stored on the run with server-assigned ids (S1, S2…); duplicate ids within a run's source set are rejected (400).
- `POST /api/draft` { runId } → { briefMarkdown, conflicts, unverifiedFlags, stats } — 409 unless the run's research completed. Drafts only from the run's stored sources; any sources in the request body are ignored. The drafting prompt requires a citation per claim; the post-pass (below) enforces it mechanically.

**Key decisions**
- *Exa over Tavily/Brave*: key already in Doppler and verified live; returns clean page contents, which citation-checking needs.
- *Citation enforcement as a post-pass, not just a prompt*: prompts leak; a mechanical check that every claim carries `[S#]` is the reliability story judges can verify (criterion 3). Post-pass semantics (tightened in the Slice 1 QA fix pass): standalone citation lines/fragments are re-attached to their claim **before** sentence-level checking; claim-bearing headings, lines ending in ":", and bold lead-ins are checked as claims (a bold lead-in is split from its body and both are checked) — exemptions remain only for purely navigational lines (the brief's title, recognised section labels with no factual content), and when in doubt a line is checked. A `[S#]` marker that does not match a real source id for the run is stripped from kept text and the sentence re-checked. Coverage is honest: with zero claims, `coveragePct` is `null` and the UI shows "no claims", never 100%.
- *No DB / no auth*: one-day cap; localStorage history is enough for the demo and removes a whole failure class. The in-memory run store is not a database — runs are never persisted and vanish with the process.
- *Server-side run store for gates and provenance* (Slice 1 QA fix pass; supersedes the earlier "browser holds the run state" and the rejection of server-side run storage below): approvals and sources must be server-side facts, otherwise a direct API call can skip the plan gate or draft from fabricated sources. In-memory only, keyed by an unguessable runId.
- *Two approval gates in the core flow*, not settings: they are the A3 trust claim and must appear in the demo.
- Alternatives rejected: LangChain/agent frameworks (overkill for 3 calls, adds unverified API surface); persistent server-side run storage (scope); streaming tokens (nice-to-have, cut for the cap).

**Risks (top 3)**
1. *Exa contents quality varies* → cap sources, prefer text-rich results, excerpt-truncate; eval set includes one niche question to prove behaviour.
2. *Drafting model ignores citation format* → post-pass enforcement + one repair retry with the offending claims listed; if still uncited, the claim is flagged, not hidden. If a draft exceeds 500 words, one shortening repair pass targets ≤450 words and the final word count is reported in the draft stats either way.
3. *One-day scope creep* → TASKS.md is the whole build; anything not in it is out of scope by definition (SPEC).

**Eval design.** `fixtures/scenarios.json`: 10 realistic questions, each with `expect: { minSources, mustCite: true, conflictExpected?: boolean }`. `scripts/run-evals.ts` drives the public HTTP flow for each scenario — `POST /api/plan`, then `POST /api/plan/approve` with the generated plan (the runner performs the approvals itself, exactly as the UI does), then `POST /api/research`, then `POST /api/draft` — and scores: completed (a final brief produced), citation coverage (% of claim lines carrying `[S#]`), conflicts surfaced vs expected. Output: a table written to `fixtures/eval-results.md`, quoted verbatim in the README.
