# BriefAgent — DESIGN

**Architecture (one paragraph).** A single Next.js (TypeScript, Tailwind) app. Run state is **stateless**: it travels in a **signed run token** held by the client (HMAC-SHA256 via Node's `crypto`, base64url payload; secret in `RUN_TOKEN_SECRET`). There is no server-side storage of any kind. Four API routes do the work, and each step verifies the token and re-signs the state for the next stage, so the gates are chained cryptographically: `/api/plan` (question → sub-questions; returns a token at stage `planned`), `/api/plan/approve` (verifies a `planned` token; returns a re-signed token at stage `approved` carrying the — possibly edited — plan), `/api/research` (requires an `approved` token; runs Exa search + contents per sub-question and returns a re-signed token at stage `researched` carrying the retrieved sources), `/api/draft` (requires a `researched` token; drafts **only from the sources inside the verified token** — a client cannot inject sources, because any change breaks the signature). The gates and source provenance are therefore enforced by the signature, not by the UI's good behaviour, and they hold on serverless deployments where consecutive requests land on different function instances that share no memory. The LLM is FastRouter; search/reading is Exa. The client keeps finished briefs in localStorage and exports Markdown. The eval runner drives the same HTTP flow headlessly (plan → approve → research → draft), performing the approvals itself.

**Data model (in-run only; carried inside the signed token, never stored server-side)**
- `RunTokenPayload`: stage (`planned` → `approved` → `researched`), question, subQuestions (the approved, edited version from stage `approved` on), and — at stage `researched` — the retrieved sources and the research warning if any sub-question's search failed. A token is `base64url(JSON payload) + "." + base64url(HMAC-SHA256)`; verification uses a constant-time comparison. Missing token → 400; bad signature or malformed payload → 401; valid token at the wrong stage → 409, each with a plain-language error.
- `Plan`: subQuestions: string[] (user-editable before approval; the approved, edited version is what gets researched).
- `Source`: id (S1, S2…), url, title, excerpt, subQuestionIndex. Inside the token, each source's text is trimmed to the 3,000 characters the drafting step actually reads, keeping the token a reasonable request body (~tens of KB for 12 sources).
- `Brief`: markdown body with inline `[S#]` citations, conflicts: { claim, positions: [{sourceId, stance}] }[], unverifiedFlags: string[].

**API contracts**
- `POST /api/plan` { question } → { token, subQuestions } — signs a stage-`planned` token. The planner guarantees 3–6 sub-questions: it retries/repairs until at least 3 are produced, or fails with a plain error.
- `POST /api/plan/approve` { token, subQuestions } → { token } — verifies the token (stage must be `planned`) and returns a re-signed stage-`approved` token carrying the edited plan.
- `POST /api/research` { token } → { token, sources, warning? } — 409 unless the token's stage is `approved`. Searches the token's approved sub-questions (identical sub-questions deduped first), one Exa call per sub-question with **per-sub-question settlement**: a failed call does not fail the run — the run proceeds with the sources that succeeded and returns a `warning`; it fails only when zero sources were retrieved. Sources are assigned server ids (S1, S2…) — unique by construction — and embedded in the re-signed stage-`researched` token.
- `POST /api/draft` { token } → { briefMarkdown, conflicts, unverifiedFlags, stats } — 409 unless the token's stage is `researched`. Drafts only from the sources inside the verified token; any sources in the request body are ignored. The drafting prompt requires a citation per claim; the post-pass (below) enforces it mechanically.

**Key decisions**
- *Exa over Tavily/Brave*: key already in Doppler and verified live; returns clean page contents, which citation-checking needs.
- *Citation enforcement as a post-pass, not just a prompt*: prompts leak; a mechanical check that every claim carries `[S#]` is the reliability story judges can verify (criterion 3). Post-pass semantics (tightened in the Slice 1 QA fix pass): standalone citation lines/fragments are re-attached to their claim **before** sentence-level checking; claim-bearing headings, lines ending in ":", and bold lead-ins are checked as claims (a bold lead-in is split from its body and both are checked) — exemptions remain only for purely navigational lines (the brief's title, recognised section labels with no factual content), and when in doubt a line is checked. A `[S#]` marker that does not match a real source id for the run is stripped from kept text and the sentence re-checked. Coverage is honest: with zero claims, `coveragePct` is `null` and the UI shows "no claims", never 100%.
- *No DB / no auth*: one-day cap; localStorage history is enough for the demo and removes a whole failure class. Nothing about a run is persisted anywhere.
- *Stateless signed run tokens for gates and provenance* (production fix, 22 Nov 2026; supersedes the Slice 1 QA fix pass's server-side in-memory run store): approvals and sources must be unforgeable facts, otherwise a direct API call can skip the plan gate or draft from fabricated sources. The run store achieved that locally but broke in production — on Vercel's serverless functions, consecutive requests land on different instances that share no memory, so `/api/research` could not find the run `/api/plan` had created ("Unknown run" on every real run). The fix keeps the guarantee and drops the storage: run state travels in an HMAC-signed token, each route verifies the signature and stage before acting and re-signs the next stage. Fabricated or edited state fails verification without the secret, exactly as it failed the store lookup before — and there is nothing to lose on a restart or a cold start.
- *Two approval gates in the core flow*, not settings: they are the A3 trust claim and must appear in the demo.
- Alternatives rejected: LangChain/agent frameworks (overkill for 3 calls, adds unverified API surface); persistent server-side run storage (scope); streaming tokens (nice-to-have, cut for the cap).

**Risks (top 3)**
1. *Exa contents quality varies* → cap sources, prefer text-rich results, excerpt-truncate; eval set includes one niche question to prove behaviour.
2. *Drafting model ignores citation format* → post-pass enforcement + one repair retry with the offending claims listed; if still uncited, the claim is flagged, not hidden. If a draft exceeds 500 words, one shortening repair pass targets ≤450 words and the final word count is reported in the draft stats either way.
3. *One-day scope creep* → TASKS.md is the whole build; anything not in it is out of scope by definition (SPEC).

**Eval design.** `fixtures/scenarios.json`: 10 realistic questions, each with `expect: { minSources, mustCite: true, conflictExpected?: boolean }`. `scripts/run-evals.ts` drives the public HTTP flow for each scenario — `POST /api/plan`, then `POST /api/plan/approve` with the generated plan (the runner performs the approvals itself, exactly as the UI does), then `POST /api/research`, then `POST /api/draft` — and scores: completed (a final brief produced), citation coverage (% of claim lines carrying `[S#]`), conflicts surfaced vs expected. Output: a table written to `fixtures/eval-results.md`, quoted verbatim in the README.
